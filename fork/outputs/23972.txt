Pieces: 7 tetrominoes. Compact encoding: each piece as a 16-bit number representing 4x4 grid, rotate by bit manipulation. Rotating a 4x4 bit grid within 16 bits: 

If bits are indexed row-major (row r, col c → bit r*4+c), rotation clockwise: new[r][c] = old[3-c][r]. As bit index: new bit (r*4+c) = old bit ((3-c)*4 + r). That's a fixed bit permutation — can be done with a lookup or arithmetic. Arithmetic rotation of 4x4 nibble grid is a bit fiddly.

Alternative: store pieces as arrays of [x,y] pairs and rotate with formula. E.g., piece = list of 4 cells. Rotate clockwise around some pivot: (x,y) -> (y, -x) then normalize. To keep it simple, use 4x4 grid coordinates 0..3 and rotate (x,y) -> (y, 3-x). This works for all tetrominoes if we place them appropriately in the 4x4 box... Actually for I piece placed in row 1 (y=1, x=0..3), rotating (x,y)->(y,3-x): (0,1)->(1,3), (1,1)->(1,2), (2,1)->(1,1), (3,1)->(1,0) — gives column x=1, y=0..3. Good, that's a valid I rotation. For 3x3 pieces (T, S, Z, L, J) placed in top-left 3x3, rotating within 4x4 with (x,y)->(y,3-x) shifts them: (0,0)->(0,3)... hmm, (x,y)->(y,3-x): (0,0)->(0,3), (1,0)->(0,2), (2,0)->(0,1). So a top row becomes left column at x=0, y=1..3. That's fine geometrically but the piece drifts to bottom-left of the 4x4 box. Repeated rotations cycle through 4 orientations, all consistent. It works — the piece just occupies different cells in the 4x4 box, which is fine as long as collision detection uses actual cell coordinates.
