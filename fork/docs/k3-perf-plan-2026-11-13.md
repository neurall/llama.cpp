Written for the hand-off to the coding model. Every number is from a run or a measurement named beside it. Rules of the repo apply (rows through `run.py run`,
answers before speeds, develop on OLMoE first, no builds during timed rows).

## Findings, by size

1. **The stream reads and uploads in turn, not together.** `cs_copy` (src/llama-moecache-fork.cpp) calls `ggml_rampool_need_fork` and blocks until the layer's
   chunk is in RAM, then queues its uploads; the scheduler thread then waits for ring blocks (`cs_done_ev`) and no read is in flight meanwhile. One pass: 221 GB
   from the SSD at 3.23 GB/s = 68 of its 77 s. At raw speed the same bytes take 41 s.
2. **A later request cuts the prompt into 3 calls**, each a full stream or chain: 190 s against 77. The compute per token is read as 57-119 ms (real: 1.6 ms
   calculated). Cause found: at the measurement (`prompt compute measured` line) `g_pp_cstream_built` is already false, so the branch for staged passes runs,
   `(time - upload estimate) / tokens`: (77241 - 20213) / 995 = 57.3146 ms, the logged value to the digit; same for both later calls. The kernel-share code of
   commit dbb36f7a4d therefore never runs. Task #303 is still open.
3. **The stream's time estimate does not count SSD reads**: 20-46 s estimated, 64-77 taken. The planner cannot see that one pass is a fixed cost of about 70 s,
   so it also offers the decode chain for 256 tokens (60 s, 316 GB uploaded).
4. **Every expert goes through CUDA0's link and ring**, also for layers 47-92 that live on CUDA1 (its link 0.00-0.3 GB/s, its 5.1 GiB of pool unused in a
   stream). Not the limit today (CUDA0's link runs at 24% of 26.7 GB/s). It becomes the limit once reads are fast: task #306.
5. **The stream takes every uncached expert of a layer** (`cs_plan`: `want` = all experts of the entry's range without a block). A short prompt touches a small
   part: 20 tokens x 16 picks is at most 320 of a layer's 896. Paris prompt: 13-26 s. This is what the predictor fetch list is for.
6. **Stream reads are admitted into the RAM pool** and evict its residents: one request evicted 61296 experts (30049 admitted, 31328 on probation), 125.7 GiB
   read into the pool. Decode after a prompt starts with a pool the stream rearranged; decode varied 1.07-2.48 t/s between requests. Task #307.
7. **Decode is not broken down yet.** Cards at 4-6% load, links 0.1-0.5 GB/s. A token needs 1472 experts; 2% fit in VRAM, 43% in RAM. Read the decode window
   lines (DEW, rampool request line: misses from RAM, from SSD, waited) before any change.

## Order of work

User's order: reads first, then the predictor. Bugs jump the queue.

### 1. Compute measurement (bug #303, small)

- In the function that logs `prompt compute measured` (src/llama-moecache-fork.cpp, about line 15274-15320): do not read `g_pp_cstream_built` there. Latch
  "this call streamed into blocks" where the pass runs (the place that sets `g_pp_cstream_built`, `llama_moe_cache_graph_built_fork`, keeps it only until the
  next graph build) and read the latch. Print the kernel share and which branch ran in the log line, so a wrong branch shows at once.
- The kernel share itself needs the wait-end stamp `tw` of stream splits (ggml/src/ggml-backend.cpp about line 4815), today only under `GGML_SCHED_PASS_STATS=1`
  (run.py sets it; users do not). Stamp it always for stream splits (one host function per expert split), or the share reads 1.0 without it.
- Check: row `k3n-1k-one`, run 2 = one stream call, compute line near 1-2 ms a token. Then Qwen3.8 `nsall-free-ns`: no change.

### 2. Read pipeline for the stream (task #308)

Goal: reads at 95% of raw (5.2 GB/s on this drive) for the whole pass, uploads beside them.

- Reads of the next chunks start as soon as the pass's layer order is known (`cs_order`, set before the pass), independent of ring blocks: a reader ahead of
  `cs_copy` by a byte budget. `ggml_rampool_ahead_fork` exists (asks without waiting); `cs_copy` keeps `ggml_rampool_need_fork` for what is still missing.
- The budget is RAM, not VRAM: the pool's probation blocks (7.5 GiB at start) or blocks taken from the coldest residents; compute it from free probation
  bytes, no fixed number.
- Stream reads do not become residents (finding 6): they leave their block when their upload is queued. This is the first half of #307.
- Check on OLMoE first (verify list, 0 bad), then K3 `k3n-1k-one`: pass line `file ... GB/s while reading` at 5 GB/s or more, pass about 45-50 s, answer
  sane. Then the `sane` list.
- Planner: the stream estimate counts SSD bytes at the measured rate (the pass line has it), and the stored SSD maximum is measured again when a pass reads
  slower than it (memory `project-ssd-slows-as-it-fills`).

### 3. Predictor fetch list in the default layout (task #281)

Today the predictor is its own mode (`pred-top=N,pred=1,predict-ahead=2`) and switches the block pool off (`pool_on ... && predict <= 0`, line about 9334).
Wanted: default layout, used before any stream, short prompts first.

- A prompt-only switch, separate from `pred_m` (19 uses, most of them decode paths of the old mode that crashed with the pool on 11-11: keep those off).
  No learned copies: `pub.pred_w` = the next layer's router (`ffn_gate_inp`), zero extra VRAM.
- Graph (src/llama-graph.cpp about 3066-3100): the next 2-3 layers' routers on the layer's input, logits to the host. Works only where the pass has a host
  sync per layer (prompt chain); the stream has none (`if (mc_cstream) { cpu_backend = nullptr; }`).
- Host: `llama_moe_cache_pp_pred_fork`, list builder `moe_fetch_list` (src/llama-moe-fetchlist-fork.h, has a unit test), then reads and uploads of the listed
  experts into pool blocks through the existing ahead code of `llama_moe_cache_pp_upload_fork` (`ring_be`, `ring_ev`, `slot_in_flight`, `set_table_entry`,
  `ahead_cps`). Today that code takes whole layers ahead only when 7/8 of a layer is touched; the list replaces that rule for short prompts. Mispredicted
  picks are fetched after the real router, as today.
- K3: a layer's blocks in the pool hold fewer than one token's 16 experts in the old per-layer layout; with the block pool the card's whole pool serves any
  layer, which is why this must run in the default layout.
- Planner: a named estimator for the list path (touched experts x bytes at SSD and link rates + compute) beside the stream's; short prompts take the list.
- Check: OLMoE (verify 0 bad, `prompt fetch list` line: share of picks in the list, too-late share), then GLM 3.5, then K3 `k3n-s` (Paris) and a 256-token
  row against today's 13-26 s and 60 s. Answers first.

### 4. Each card streams its own layers (task #306)

Both links, both rings, both pools. Worth it after step 2 (the link then carries 5+ GB/s from the SSD plus the RAM part at once) and needed for two SSDs.

### 5. RAM pool admission by reads per residence (task #307, second half)

User's design in memory `project-rampool-eviction-history`. Measure decode first (finding 7).

### 6. Attention from a side file (tasks #304, #305)

User, today: no requant at load. A tool writes the requantized attention tensors into a side GGUF once; a loader switch takes those tensors from it. The same
switch later takes tensors quantized once from the full-resolution HF files. First test: Q4_K to Q3_K, speed only (3-4 GiB more pool on 15.5 GiB of attention).
