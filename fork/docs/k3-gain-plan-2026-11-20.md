# Kimi K3.1 on PC1: where the next gains are (2026-11-20)

Hand-over. Read `k3-perf-plan-2026-11-13.md` first (machine, model, read pipeline). Rules of the repo apply. Numbers below are from the server logs named.

## What limits K3 today

| fact | value | source |
|---|---|---|
| experts | 92 layers x 896, 16 picks a token and layer = 1472 picks a token, 6.15 MiB each (3 slices) | pool lines |
| VRAM | 2% of the experts (about 900 blocks a card); 3% of picks hit it cold, 6.5% with heat | rampool request lines |
| RAM pool | 167 GiB today (a 50 GiB tmpfs file was in the way, removed 08:30), 224-229 GiB on 11-16 | pool lines |
| SSD | one drive, 5.4 GB/s raw | fio, 11-13 |
| pass cap | 5152 tokens: the context fits no larger compute buffer beside 16 GiB of dense weights a card (not the mask budget, whatever the log line says) | common_init_result lines |

Decode, measured:

| run | RAM pool | misses from RAM | SSD read a token | SSD time a token | token time |
|---|---|---|---|---|---|
| 11-16 `latest-k31-i` (13k + 1k, heat file, old CPU path) | 224 GiB | 70% | 1.74 GiB | 0.32 s | 0.60 s |
| 11-16 `latest-k31-o` (short + 930, heat file) | 229 GiB | 80-81% | 1.35 GiB | 0.25 s | 0.55-0.59 s |
| 11-20 `rc_bell_cmp-k31-cmp` (1k + 256, clean state, new pool path) | 167 GiB | 60-67% | 3.4 GiB | 0.63 s | 0.63 s |

Cold, decode runs exactly at the drive's rate: t/s = 5.4 GB/s / SSD GiB a token. With heat the SSD is about half the token; the rest was the old CPU path.

Prompt: every pass reads the experts that are not in RAM, (508 - pool) GiB at 5.4 GB/s = 52-63 s, whatever the pass holds. 13k tokens = 3 passes = 308 s
(42 t/s); 1k tokens = 1 pass = 77-116 s.

How much the hottest experts cover (lifetime counts of the heat file of 11-16, 9895 decode tokens, `globalhot.ini`):

| share of experts held | 2% | 10% | 20% | 33% | 40% | 43% | 50% | 60% |
|---|---|---|---|---|---|---|---|---|
| uses covered | 20.7% | 47.8% | 63.4% | 76.0% | 81.0% | 82.9% | 86.8% | 91.3% |

So with ideal residents (2% VRAM + 43% RAM) the SSD serves 16% of picks = 1.41 GiB a token = 0.26 s. 11-16 was at 19-21%: the RAM set is near its ideal,
the VRAM set is not (6.5% of picks against 20.7% possible).

## Opportunities, by gain per work

| # | what | expected | work |
|---|---|---|---|
| 1 | Second SSD: every other shard on nvme0n1 (Lexar NM710, 931 GiB, unmounted, 600 GiB LVM volume), links in /m/k/1 | reads up to 2x: prompt pass 52-63 s to about 30 s, decode SSD part halved (decode +30-60%) | user mounts the drive and copies 16 shards (270 GiB); code: check that the reader keeps 32 reads in flight per drive, not in total (`ggml-read-fork.h`, `ggml-rampool-fork.cpp` readers) |
| 2 | Layer-major prompt: for each layer run all the prompt's passes, then the next layer, so a prompt streams the experts ONCE, not once per pass | 13k prompt: 3 streams to 1 = about 3x (42 to 120+ t/s); 60k: 12x fewer SSD bytes | large: per-layer graphs, hidden state of all tokens carried between layers (13k x n_embd floats = 190 MB), KV written per layer and chunk. Same gain on every model whose prompt is SSD-bound |
| 3 | VRAM holds the hottest 2% at decode | picks from VRAM 6.5% to up to 20%: 15% fewer CPU experts and SSD bytes | read the K3 rows of today first (ring-cold=2 may already keep them through a prompt); then preload from the heat map after each prompt before decode starts |
| 4 | Read ahead in decode from the next layers' routers (the fetch-list builder exists: `llama-moe-fetchlist-fork.h`) | only if the token is NOT at the drive's rate: token = max(SSD, compute) instead of the sum, up to +50% | medium; pointless while decode is SSD-bound, so measure first |
| 5 | Fetch list for prompts of 64-500 tokens (task #281) | 25-35% of a pass's reads; nothing from 1k tokens up (a 1k prompt touches nearly every cold expert) | medium; short prompts already take the decode chain |
| 6 | Attention as Q3_K from a side file (tasks #304, #305) | headers, 2026-11-20: attention 15.50 GiB Q4_K, with ssm_g 18.68 GiB; as Q3_K 14.27: about 2.2 GiB a card (1.8 without ssm_g; first estimated 3-4). Pool about 6.2 to 8.4 GiB a card (+35%, not twice); pass cap 5152 to about 7200 if the graph gets the 2.2 GiB (lend 1.05-1.11 MiB a token at 10240 cells), so a 13k prompt in 2 passes | done: `--moe tensor-file`, `fork/attn_side.py` (copy, quant, hf), rows `fork/runs/sidefile.csv`; quality: paired PPL; the full-resolution BF16 fetch (71.3 GB) after the Q3_K speed rows |
